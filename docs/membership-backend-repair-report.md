# 会员与礼品卡后端修复报告

检查范围为会员与礼品卡的下单、确认付款、链上收据入账、兑换、作废退款和账户历史。复现与回归使用隔离的 SQLite 数据库和模拟 RPC。取消订单的资金截止点使用新增的快照表和触发器，首次使用时自动初始化，不需要手动回填。回归验证仅使用本地数据。

## 已修复

| 问题 | 复现结果 | 修复后的行为 |
| --- | --- | --- |
| 两个购卡入口各自校验幂等键 | 同一账户先预留礼品卡订单，再以同一键直接购卡。余额被扣除，原订单之后因卡片唯一键冲突无法结算。 | 两个入口在写入事务内互查同一键。待付款预留同键直接购卡返回冲突，已完成且参数匹配的购卡重试返回原卡。 |
| 不同请求临时复用待付款订单 | 新键曾返回成功和旧订单，但没有保存这个键。旧订单完成后重试新键会创建另一笔待付款单。两笔并发预留也可能返回通用 503。 | 只有相同键和相同购卡条件才重放。其他请求返回 409 和当前待付款订单。并发插入失败后按相同规则重读。 |
| 重试确认链上付款时扫描器先完成结算 | 账本已确认收款，接口仍返回“订单不可用”。 | 礼品卡和会籍确认接口按订单与账户重读，已结算时返回原结果。礼品卡详情的按需结算也绑定正在查看的订单。 |
| 两次余额付款确认恰好用完全部余额 | 后到的请求已读到待付款订单，随后只看到先到请求扣完后的余额，可能返回“余额不足”。 | 礼品卡和会籍显式付款按原订单核对结算状态。并发完成时返回已有回执，余额只扣一次。 |
| 订阅卡兑换重试没有校验目标订单 | 同一兑换请求首次成功后，把目标换成任意其他订单仍返回同一成功回执。 | 新兑换在同一事务中记录首次请求的订单。重试须匹配原订单。历史回执允许原有无目标重试，带目标的重试须匹配当时被兑换关闭的订单。 |
| 余额卡独立兑换忽略订单字段 | 调用方提供订单时，余额卡仍被当作独立充值，卡已使用但订单未支付。 | 独立兑换拒绝订单字段，余额卡订单付款继续使用专用接口。 |
| 链上交易哈希的大小写影响去重 | 同一链、同一哈希和日志索引，哈希大小写不同会被记录成两笔收据。 | 新收据使用小写哈希。初次查询与事务内复核均识别旧收据中的不同大小写，同一日志只入账一次。 |

| 已取消订单的到账显示随之后充值增长 | 订单取消后继续充值，旧订单的“已收到”仍增加。 | 新取消订单在取消事务内保存资金游标；同一毫秒内的后续充值只增加钱包。旧订单按取消时间保守估算；过期订单还受订单到期时间限制。 |

## 验证

- `node scripts/membership-checkout-race-test.mjs` 覆盖跨入口冲突、并发下单、重复付款、扫描与确认同时完成。
- `node scripts/membership-billing-test.mjs` 覆盖余额、赠金、锁价和同一链上收据的不同大小写重放。
- `node scripts/membership-gift-test.mjs`、`node scripts/subscription-gift-test.mjs`、`node scripts/admin-gift-issuance-test.mjs` 覆盖卡号权限、兑换后重试、退款和管理员发卡。
- `npm run test:membership` 的账本测试更新为当前的预留下单和链上付款确认流程。UI 夹具改用与 Node 请求兼容的取消信号，并在报价刷新后检查焦点恢复。
- `npm test` 主仓库回归通过。优惠码和归集专项回归也通过。

## 待处理

链上去重由主应用与扫描服务共用。发布这批改动时，两者均需更新。

- 历史上已经发生的跨入口冲突和疑似重复链上入账需要对账。本次修复阻止新的冲突或重复入账，没有自动撤销旧流水、调整余额或重写旧订单。
- 三个单独执行的旧脚本仍依赖旧版订单接口或按订单分配收款地址的模型。它们分别是 `scripts/membership-test.mjs`、`scripts/membership-scanner-test.mjs` 和 `scripts/membership-flow-test.mjs`。本次只更新了 `npm run test:membership` 的主测试夹具。
