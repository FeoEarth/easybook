# PDF reader initialization regression

The build94 Android failure occurred before PDF.js or attachment bytes were consumed: `mountGlass()` registered listeners using `vp`, which was only declared inside its separate `sync()` function. Android calls mountGlass; Web returns before that statement. The resulting ReferenceError occurred before filename assignment and outside the reader's try block. `openAttachment()` called `void reader.open()`, leaving the rejected initialization unobserved. The empty title plus its down-chevron looked like `v`, while the initial status remained forever.

Use window.visualViewport in the adapter's listener scope. Assign sanitized metadata before native initialization, initialize inside the guarded path, and await reader.open at the sole PDF attachment entry. The reader owns cancellable Blob/URL byte loading, resource/parse timeouts, first-render watchdog, errors, retry and back. HTTP failures are checked before parsing; data supplied to PDF.js is copied because its Worker transfers the buffer, preserving retry input. Close aborts file fetches and clears rendering timers; stale opens cannot update a new session.

There was no second legacy PDF renderer on main. The generic attachmentDialog title and actions serve images/audio/video too and cannot be deleted without affecting other media. PDF mode hides them immediately, including during loading. Removed the redundant eager module script and obsolete pdf-controls-hidden cleanup state. All note/attachment PDF actions still pass through openAttachment into this single reader; shared save/share handlers are retained. No iframe/object PDF fallback exists.

Changed PDF reader, native glass adapter JS, PDF CSS, PDF caller in index.html, generated worker/ui.mjs, focused integrity script, release workflow, versionCode 53 and this note. No attachment model, compression, limits, sync protocol, Worker backend or QWEA0 engine changes.

Validation: scripts/pdf-reader-integrity.mjs uses jsdom and @napi-rs/canvas (PDF.js dependency) without a browser, UI automation or emulator. It runs the real reader and PDF.js Worker/parser/viewer against a generated valid PDF, checks actual red page pixels and pagerendered completion, page count, filename, close and reopen; repeats with a NativeStore bridge stub to exercise the formerly failing Android-only path. It also checks malformed-PDF visible failure, retry/back availability and filename fallback. This is not an Android runtime or Cloudflare integration test. Native WebView local attachment streaming, cloud PDF on a device, real touch/zoom/search/share and glass placement remain unverified. No Cloudflare deployment is needed or performed.
